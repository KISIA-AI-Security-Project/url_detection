# 모든 URL에 적용하는 쉬운 빠른 분석 결과

## 현재 공통 처리 — 2026-10-06 후속 적용

현재 운영은 EC2 준비된 작업자, Context 20·Judgment 28·L23 19·Gate2·Result5를 사용한다. 모델은 Sonnet 5.5/high/8192다. 다섯 판정 지시문을 적용했으며 이번 변경에서 수집·record·Builder 본문은 바꾸지 않았다. 아래 Django·Context 19·Judgment 25 및 네 판정 v5 기록은 이전 적용 당시의 증거다.

- 순수 객체·배열로 선언된 JavaScript 콘텐츠도 수집한다. 같은 객체에 있는 문구·버튼·주소 관계를 Builder가 선별하고 쉬운 설명을 만든다. 원문·전체 값·출처는 raw/native/record에 보존한다. 선언된 내용을 실제 화면 표시·클릭·정보 전송으로 설명하지 않는다.
- 기존 정적 분석·HTTP/TLS 기능은 유지한다. 새 정보는 기존 분석에 추가되며, 사이트명·URL·브랜드별 예외는 없다. 같은 주소 목록과 설정을 본문에 반복하지 않는다.
- 모델은 정상·정상 가능성 높음·악성 가능성 높음·악성·판단불가 중 하나를 선택한다. 현재 용도·기능·연결 관계가 충분하면 정상 또는 악성이다. 가능성 등급에는 현재 핵심 관계의 구체적인 공백이 필요하며, 판단불가는 다른 계층까지 종합해도 어느 방향을 지지하는지 정할 수 없을 때만 사용한다. 운영자 미확인·미래 사용 가정·추가 피해 미관측만으로 유보하지 않는다. 가능성 등급과 판단불가의 공백은 내부 `decision_notes`에만 보존한다. 이전 `SUSPICIOUS` 결과는 그대로 읽는다.
- 서버는 이번 Builder에 실제 존재하는 항목 이름만 연결한다. 표기 차이와 제한된 한글 오타를 허용하지만 후보가 여럿이거나 항목이 없으면 연결하지 않는다. 판정·요약·이유를 코드가 다시 쓰지 않는다. 이름이 연결됐다고 이유의 의미까지 검증됐다고 보지 않는다.

새 URL을 보기 전에 서비스 소스와 공통 지시를 고정하고, 그 뒤 선정한 다섯 주소를 실제 Cognito Front에서 한 번씩 접수했다. 데이터셋 출처와 분류는 모델 입력에 넣지 않았고 VT는 요청하지 않았다. 이 결과에 맞춰 코드를 바꾸거나 특정 사이트 예외를 추가하지 않는다. 정상 가능성 높음 2건·악성 1건·의심 1건·판단불가 1건을 관측했으며, 이 작은 묶음으로 전체 정확도나 과적합 부재를 증명하지 않는다. 이유의 적합성·표현·모델 판정 변동은 실제 원본과 별도로 검토한다.

### 직전 네 판정 v5의 확인 범위와 남은 문제

다섯 실제 요청의 원본·record·실제 모델 본문·공개 결과가 같은 입력에 연결됨을 독립 검토했다.
그러나 한 의심 응답은 근거 없는 정식 미러·제휴 가설을 사용했고 공개 이유에 미확인 내용을
반복했다. 다른 응답에는 등록 만료·네트워크 조직을 과도하게 표현한 문장이 남았다.
중첩 JavaScript 전송 구문의 일부도 기존 native 분석 범위 밖이다. 이름 연결 성공이나
결과 수신 성공을 판정 품질 해결로 보고하지 않는다. 추가 분석기 확장은 보류했다. 이후 다섯 판정 지시문 적용은 이 분석 범위를 바꾸지 않는다.

## 책임

| 내용 | 만드는 주체 | 사용 범위 |
|---|---|---|
| 판정·짧은 요약·이유 | 기존 판정 모델 호출 1회 | 같은 Builder 본문 전체를 읽고 판정한다. 이유는 중요도 순서로 짧게 설명한다. |
| 확인된 사실의 쉬운 설명 | Builder의 공개 항목 생성 코드 | 이미 같은 항목에 선별된 값·관계·조건으로 작성한다. URL별 사전이나 fact_id별 문구를 사용하지 않는다. |
| 기술 정보 | 기존 Builder 공개 사실 | `facts[].text`와 제목·ID·근거 관계를 유지한다. |
| 화면·펼침·이동 | Front | 모델 이유가 연결한 사실을 표시하며 같은 사실 카드를 중복 작성하지 않는다. |

쉬운 설명은 기존 공개 항목의 사실과 관계로 생성한다. 전체 상세를 LLM으로 다시 쓰지 않는다. 후속 다섯 판정 보완은 같은 모델 호출의 지시와 응답 계약에 적용하며 모델 설정·수집 기능·Builder 선별은 유지한다.

## 공개 형식

기존 `fast-result-1`의 fact에 다음 선택적 필드만 추가한다.

```json
{
  "fact_id": "기존 ID",
  "title": "기존 제목",
  "kind": "fact",
  "text": "기존 기술 정보",
  "basis": {"kind": "observed_response", "label": "기존 근거 종류"},
  "condition_fact_ids": [],
  "plain": {"title": "쉬운 제목", "text": "같은 사실의 쉬운 설명"}
}
```

`plain` 내부 키는 `title`, `text` 두 개만 허용하며 둘 다 빈 값이 아닌 문자열이다. 기존 저장 결과에는 `plain`이 없어도 읽을 수 있다. 새 결과를 만드는 현재 공개 생성 지점에는 공통 설명을 붙인다. 새 항목 종류를 추가할 때도 그 생성 지점의 쉬운 설명을 함께 추가한다. `context_revision`과 `result_revision`은 쉬운 설명도 포함한다.

Context·Judgment·Result의 공개 형식 검사 코드를 함께 배포해야 한다. 과거 Result의 정확한 6필드 검사는 새 `plain`을 거부하므로 생산자만 갱신하지 않는다.

## Front 사용

참조 구현은 `frontend/fast-result-renderer.js`의 `FastResult.render(root, result, {url})`이다. `result`에는 GET 결과 API가 반환한 JSON을 그대로 전달한다. `url`은 Front가 현재 요청과 연결해 보관한 입력 주소다.

```js
FastResult.render(document.querySelector('#analysis'), apiResult, {
  url: submittedUrl
});
```

기본 화면에는 판정, 모델의 짧은 요약, 중요도 순서의 이유 최대 3개를 표시한다. 이유가 더 있으면 `판정 이유 더 보기`로 전부 볼 수 있다.

`이유의 근거 보기`는 `related_fact_ids`를 `details.facts`에서 찾아 같은 카드를 표시한다. 해당 사실의 조건 링크가 있으면 함께 표시한다. 연결할 실제 ID가 없는 이유에는 근거 이동 버튼을 만들지 않는다. Front가 관련 항목을 추측하거나 비슷한 ID로 바꾸지 않는다.

상세의 기본 문구는 `plain.title`, `plain.text`이며 `기술 정보 보기`를 펼치면 기존 `text`를 확인한다. `확인된 내용 더 보기`에서는 모든 공개 사실을 확인할 수 있다. 기존 결과에 `plain`이 없으면 기존 제목과 기술 정보 펼침으로 읽는다. 서버 결과를 `textContent`로 표시하여 페이지 문구나 코드가 화면에서 실행되지 않게 한다.

`judgment_status`가 `accepted`일 때만 판정을 표시한다. `pending`, `not_requested`, `failed`, `invalid`는 각각 처리 상태로 표시하며 임의의 판정으로 바꾸지 않는다. 원본·Record·S3 매핑·수집 한계 목록은 사용자 화면에 전달하거나 표시하지 않는다.

## 확인 범위

같은 실제 저장 입력의 기존 상세 사실·모델 본문·공개 구획·내부 매핑·입력 객체를 전후로 비교한다. `plain`만 추가됐을 때 기존 기술적 의미가 달라지지 않아야 한다. 이 검사는 모든 웹사이트의 판정 품질을 보장하는 검사가 아니다.

새 URL에서는 실제 공개 POST → EC2 수집·Builder → Sonnet 5.5 → 공개 GET 결과를 확인하고, 그 JSON으로 참조 화면을 생성한다. 출력 문구를 사례별로 수작업 수정하지 않는다. 실제 실행 시간은 공개 결과 수신, 서버 단계, 모델 호출 시간을 구분해 기록한다.

## AWS 적용과 실제 화면 확인 — 2026-10-06 초기 적용 기록

현재 적용된 버전은 Context 19, Judgment 25, Result 4다. EC2의 기존 수집·Builder 실행 경로에 공통 설명 코드를 적용했다. 판정을 수행할 때 기존 Sonnet 5.5 호출 1회를 사용하며, 쉬운 설명을 위한 추가 호출은 없다. 사용자 문구에 관한 지시만 보완했다.

새 주소 `https://www.djangoproject.com/`의 실제 공개 POST → GET 결과는 `accepted`, `LIKELY_BENIGN`이다. 공개 사실 100개에 모두 `plain`이 있다. 이 실제 JSON을 공통 렌더러에 그대로 전달한 결과에서 기본 이유 3개, 펼친 이유 5개, 근거 이동, 기술 정보 펼침, 전체 사실 100개와 중복 없는 카드 표시를 확인했다.

첫 실제 실행에서 공유 이미지의 크기·형식 설정이 페이지 문구처럼 설명되는 문제와 연결 폼이 없는 버튼 표현을 확인해 공통 생성 규칙을 수정했다. [Open Graph의 속성 정의](https://ogp.me/)에 맞춰 설정 종류를 구분하고 실제 이미지 측정으로 설명하지 않는다. 특정 사이트에 대한 예외는 추가하지 않았다. 같은 주소의 후속 실제 실행에서도 수정된 설명이 전송·표시됐다.

| 검증 | 확인한 범위 |
|---|---|
| 같은 저장 입력 전후 대조 | Django·Rust·Mozilla·PostgreSQL·Python의 623개 사실에서 기존 사실, 모델 본문, 구획, 내부 매핑이 같다. 쉬운 설명만 추가됐다. |
| 계약 회귀 검사 | 공개 형식·모델 선언 필드·결과 API 읽기 등 의미 있는 검사 47개 통과. |
| 독립 검토 | 최종 실제 원본 → record → 모델 입력 → 모델 응답 → 공개 GET/S3 결과와 근거 연결을 대조했다. |
| 브라우저 | 같은 공통 렌더러로 실제 결과의 기본 화면·이유 펼침·근거 이동·기술 정보·전체 사실 표시를 확인했다. |

새 URL마다 위 생성 규칙을 적용하며 사이트명이나 fact ID로 설명을 선택하지 않는다. 현재 지원하는 항목 종류 전체에 적용되는 구조를 확인한 것이며, 모든 URL의 내용이나 모델 판정 정확도를 검증했다고 해석하지 않는다. 새 항목 종류를 만드는 개발자는 그 항목의 쉬운 설명도 생성 지점에 정의해야 한다.

후속 실제 실행의 POST 시작 → 최종 GET 응답 수신은 **10.847638초**, 모델 서비스 요청·응답은 **7.876147초**, 이를 제외한 전체 구간은 **2.971491초**다. EC2 수집·Activity·Builder 묶음은 그 안의 **1.471302초**다. 모델 서비스 요청·응답에는 네트워크·원격 처리가 포함되며 순수 추론 시간으로 확정하지 않는다. 이번 변경은 사용자 설명과 화면의 일반화 검증이며 별도 성능 개선율을 주장하지 않는다.

실제 화면과 실행 자료는 `evaluation/remediation-20261006/public-explanations/new-url-test/` 아래 `django-final-result.html`, `aws-final/`, `timing/TIMING.md`, `independent/AWS-FINAL-REVIEW.md`에 보존했다. 화면은 원본 GET JSON과 공통 렌더러를 포함하는 단독 HTML이어서 서버 없이도 같은 공개 결과를 열어 볼 수 있다. 운영 Front에는 JSON을 현재 요청 URL과 함께 전달하고, 이 참조 HTML의 레이아웃과 펼침 동작을 사용한다.
